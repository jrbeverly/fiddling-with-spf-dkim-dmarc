# SPF, DKIM, and DMARC

Second draft. Revised section by section from `v1.md` in response to the alignment, compression, and editorial review findings; per-finding dispositions are recorded in `../review/revision-log.md`. Not yet verified; the verification review follows.

## 1 · The Problem Email Authentication Addresses

SMTP (RFC 5321) does not authenticate the claimed sender of a message. Any MTA can issue `MAIL FROM:<anything@example.com>` without proving control of that domain.

The `From:` header shown to users (RFC 5322) is also unverified, and it can differ from the envelope sender.

Together these properties enable domain spoofing: delivering mail that appears to come from a trusted domain while originating from an attacker-controlled server. The attacks this enables:

- **Phishing via brand impersonation** — mail that appears to come from a bank, retailer, or platform, harvesting credentials.
- **Business email compromise (BEC)** — mail that appears to come from an executive or vendor, directing payments.
- **Spam delivery hiding its real origin.**

SPF, DKIM, and DMARC are layered mechanisms that together allow a receiving server to verify claims about message origin and to act on verification failures.

## 2 · SMTP Identities Relevant to Authentication

Three distinct domain identities appear in a mail transaction; they can all differ. Every mechanism in this document operates on one of them, so they come first.

- **RFC5321.MailFrom (envelope sender)** — the domain in the `MAIL FROM:` SMTP command. It is used by the SMTP infrastructure for bounce delivery (DSNs) and is not normally visible to end users. This is the identity SPF checks. [RFC 7208 §2]
- **RFC5322.From (header From)** — the `From:` header field in the message body. This is what the user sees as the apparent sender. SPF and DKIM do not check it directly; DMARC uses it for alignment. [RFC 7489 §3.1] A message can carry multiple `From:` addresses (rare); DMARC evaluates against the organizational domain of the first address (defined in section 10). [RFC 7489 §5.6.1]
- **DKIM signing domain (`d=`)** — the domain that generated the DKIM signature, recorded in the `DKIM-Signature` header. It is independent of both other identities: a third-party signer puts its own domain in `d=` unless it signs with the From domain. DMARC alignment checks it against RFC5322.From. [RFC 6376 §3.5, RFC 7489 §3.1.2]

## 3 · DNS as Part of the Authentication Model

SPF and DKIM both store authentication data in DNS TXT records.

DNS serves as a trusted distribution channel for policy and public keys because the domain owner controls it: anyone can query the records, but only the owner can publish them.

DNSSEC can authenticate DNS responses, but SPF, DKIM, and DMARC do not require it — the owner-control premise alone is the basis.

A receiving server performs DNS lookups at delivery time to retrieve current policy.

## 4 · How the Mechanisms Layer Together (Overview)

Before any record syntax, the shape of the whole system:

- **SPF** answers: did the sending IP have permission for the envelope (RFC5321.MailFrom) domain?
- **DKIM** answers: does a valid signature vouch for this message?
- **DMARC** ties whichever results exist to the visible From domain and applies policy.

DMARC is the decision layer, not an authentication mechanism itself: it decides what the SPF/DKIM results mean for the domain the user sees, and what the receiver should do when they fall short. The step-by-step mechanics of the full evaluation are in section 14.

## 5 · SPF: Record Syntax

Standard: RFC 7208.

**Location.** The SPF record is a TXT record published at the RFC5321.MailFrom domain. Example lookup: `dig TXT example.com`. When MAIL FROM is empty (a bounce message), the HELO/EHLO domain is checked instead. [RFC 7208 §2.3]

**Prefix.** Records begin with `v=spf1`.

**Mechanisms.** Evaluated left-to-right; the first match wins.

| Mechanism | Matches when |
| --- | --- |
| `all` | Always; used as the catch-all terminator |
| `include:<domain>` | The named domain's own SPF record authorizes the IP (recursive evaluation; counts toward the DNS lookup limit) |
| `a[:<domain>]` | The sending IP is listed in the domain's A/AAAA records |
| `mx[:<domain>]` | The sending IP is among the A/AAAA addresses of the domain's MX hosts |
| `ip4:<address/cidr>` | The sending IP is the given IPv4 address or inside the CIDR block |
| `ip6:<address/cidr>` | The sending IP is the given IPv6 address or prefix |
| `ptr[:<domain>]` | Reverse-DNS match; deprecated and discouraged [RFC 7208 §5.5] |
| `exists:<domain>` | The domain has any A record |

**Qualifiers.** Prefixed to a mechanism:

- `+` Pass — default if omitted; the sending IP is authorized.
- `-` Fail — the sending IP is not authorized; reject recommended.
- `~` SoftFail — the sending IP is probably not authorized; accept but mark.
- `?` Neutral — no assertion either way.

**Modifiers.**

- `redirect=<domain>` — replace the current record with the named domain's SPF record; used for shared SPF policies.
- `exp=<domain>` — provides a human-readable explanation for failures.

**Example**

```
v=spf1 ip4:203.0.113.0/24 include:_spf.google.com ~all
```

The record authorizes `203.0.113.0/24` outright, delegates the rest of the decision to `_spf.google.com`'s record, and soft-fails anything neither covers.

## 6 · SPF: Evaluation Algorithm

The receiver's execution of the record learned above. [RFC 7208 §4]

1. Extract the RFC5321.MailFrom domain (or the HELO domain if MailFrom is empty).
2. Retrieve the TXT record at that domain.
3. The record must begin with `v=spf1`; multiple matching TXT records → PermError.
4. Evaluate mechanisms left-to-right. On a match, return that qualifier's result. No mechanism matches → implicit Neutral.
5. DNS lookup limit: at most 10 DNS-dependent lookups per evaluation (`include`, `a`, `mx`, `ptr`, `exists`, `redirect`); exceeding → PermError. [RFC 7208 §4.6.4]
6. Void lookup limit: at most 2 lookups returning zero records (NXDOMAIN or no results); exceeding → PermError. [RFC 7208 §4.6.4]

Possible results: Pass, Fail, SoftFail, Neutral, None (no record), TempError, PermError.

## 7 · DKIM: Signature Structure

Standard: RFC 6376. A DKIM signature is added as a `DKIM-Signature:` header field before transmission. The sender signs with a private key it controls; the receiver later verifies with the matching public key (sections 8 and 9).

**Required tags**

- `v=` — version; currently `1`.
- `a=` — signature algorithm; `rsa-sha256` (recommended) or `rsa-sha1` (deprecated in RFC 8301).
- `b=` — base64-encoded signature value.
- `bh=` — base64-encoded hash of the canonicalized message body.
- `d=` — signing domain (used for public key lookup and DMARC alignment).
- `h=` — colon-separated signed header field names, in the order signed.
- `s=` — selector.

**Common optional tags**

- `c=` — canonicalization for header and body; format `<header>/<body>`; values `simple` or `relaxed`; default `simple/simple`. [RFC 6376 §3.4]
- `i=` — agent or user identifier (AUID); often `@<d>` or a specific address; must share the domain in `d=`.
- `t=` — signature timestamp (Unix time).
- `x=` — signature expiration (Unix time).
- `l=` — number of octets of the body covered by `bh=`; lets content be appended without breaking the signature.

**Canonicalization** (`c=`) decides how tolerant the signature is of transport changes:

- `simple` — whitespace and line endings preserved as-is; fragile to minor reformatting.
- `relaxed` — collapses runs of whitespace, lowercases header names, strips trailing whitespace; tolerant of minor modification by intermediaries.

This is why minor transport changes can break verification: verification recomputes the hash and signature over the received bytes, and any change the chosen canonicalization does not erase produces a mismatch.

**Example**

```
DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed;
  d=example.com; s=20230101;
  h=from:to:subject:date:message-id;
  bh=<body-hash>;
  b=<signature>
```

## 8 · DKIM: Selectors

A selector is a string identifying which public key to retrieve — the `s=` tag resolved. [RFC 6376 §3.1, §3.5] The key record is a TXT record at the name built from the selector and the signing domain:

```
<selector>._domainkey.<domain>
```

Example: `20230101._domainkey.example.com`.

Multiple selectors can be active simultaneously, which enables key rotation and per-service keys: old and new keys coexist during a rotation, and each signing service gets its own selector, under which the domain owner publishes the corresponding public key.

**Key record tags** (at `<selector>._domainkey.<domain>`)

- `v=DKIM1` — version; recommended but optional.
- `k=` — key type; `rsa` (default) or `ed25519` (RFC 8463).
- `p=` — base64-encoded public key; an empty value means the key has been revoked.
- `t=y` — testing mode; receivers should not apply policy but still verify.
- `t=s` — strict subdomaining; the `i=` AUID must have `d=` as its exact domain (no subdomain match).

## 9 · DKIM: Key Lookup and Verification

The receiver-side procedure that completes DKIM. [RFC 6376 §6]

1. Locate `DKIM-Signature` header(s) in the received message.
2. For each signature, extract `d=` and `s=`.
3. Query DNS for the TXT record at `<s>._domainkey.<d>`.
4. Retrieve the public key from the `p=` tag.
5. Recompute the body hash using the algorithm in `a=` and the body part of `c=`; compare to `bh=`.
6. Reconstruct the canonicalized headers listed in `h=`; verify the signature in `b=` against those headers and the body hash using the public key.
7. Signature verifies → DKIM pass for domain `d=`.

Two outcomes that are easy to conflate:

- A **failing** signature does not always mean fraud; it may indicate modification in transit.
- A **missing** signature means no DKIM result, not a failure.

**Oversigning** — signing a header name that is absent in the message prevents intermediaries from inserting that header: the signature does not cover it, so if one is inserted, verification recomputes over a header set that now includes it and fails. [RFC 6376 §8.15]

## 10 · DMARC: Identifier Alignment (Strict vs. Relaxed)

SPF and DKIM each authenticate an identity of their own choosing: SPF proves something about the envelope domain, DKIM about the signing domain. [RFC 7489 §3.1] Alignment is DMARC's central idea: it asks whether either result vouches for the From domain. Authentication without alignment does not protect the visible From domain — an attacker can pass SPF for a domain they control while spoofing From.

DMARC compares the authenticated identity against RFC5322.From under one of two modes:

- **Relaxed alignment** — subdomains allowed: `mail.example.com` aligns with `example.com`. The comparison uses the organizational domain — the registered domain under a public suffix (`sub.example.com` → `example.com`), determined using the Public Suffix List. This is the default mode.
- **Strict alignment** — exact match required between the checked identity domain and the RFC5322.From domain; no subdomain tolerance.

**Implications.** Strict alignment requires the authenticated domain to equal the From domain exactly, so senders must present the same domain in both identity fields.

## 11 · DMARC: Policy Options

Standard: RFC 7489.

**Location.** The DMARC record is a TXT record at `_dmarc.<domain>`. Example lookup: `dig TXT _dmarc.example.com`.

**Prefix.** Records begin with `v=DMARC1`.

**`p=`** — the policy applied to the organizational domain of the RFC5322.From. [RFC 7489 §6.3]

- `none` — no action on failing messages; reporting only. Used during initial deployment to observe without consequences.
- `quarantine` — deliver to spam/junk or otherwise flag for review.
- `reject` — reject the message at the SMTP level (or discard after acceptance).

**`sp=`** — subdomain policy; overrides `p=` for subdomains of the From domain that do not have their own DMARC record. Same values as `p=`. [RFC 7489 §6.3]

**`pct=`** — integer 0–100; the fraction of messages to which `p=` applies; the rest receive `none` treatment. Used for gradual rollout. [RFC 7489 §6.3]

**Alignment mode tags** — `adkim=r` (default) or `s` for DKIM; `aspf=r` (default) or `s` for SPF. These select the strict/relaxed modes of section 10, per path.

**Reporting tags**

- `rua=` — comma-separated URIs for aggregate report delivery (e.g., `mailto:dmarc-reports@example.com`).
- `ruf=` — comma-separated URIs for failure (forensic) report delivery; see section 15.
- `fo=` — failure reporting options: `0` (default; report if both SPF and DKIM fail), `1` (report if either fails), `d` (DKIM failure), `s` (SPF failure).

**Example**

```
v=DMARC1; p=quarantine; adkim=r; aspf=r; pct=100; rua=mailto:dmarc@example.com
```

## 12 · SPF Alignment

The alignment concept of section 10 applied to the SPF path. [RFC 7489 §3.1.1]

DMARC defines SPF alignment as the RFC5321.MailFrom domain compared against RFC5322.From.

- **Relaxed alignment** (default, `aspf=r`) — the organizational domains (section 10) must match. MailFrom `bounce.example.com` + From `user@example.com` → **aligned**.
- **Strict alignment** (`aspf=s`) — exact domain equality required. The same pair → **not aligned**.

Bounce addresses commonly sit on a subdomain of the sending domain, and relaxed mode — the default — accepts exactly that pattern.

## 13 · DKIM Alignment

Symmetric to section 12, for the DKIM path. [RFC 7489 §3.1.2]

DMARC DKIM alignment compares the `d=` tag of a passing DKIM signature with the RFC5322.From domain.

- **Relaxed alignment** (default, `adkim=r`) — the organizational domain of `d=` must equal the organizational domain of the header From. `d=mail.example.com` + From `user@example.com` → **aligned**.
- **Strict alignment** (`adkim=s`) — exact domain equality required. The same pair → **not aligned**.

A message may carry multiple DKIM signatures; DMARC passes via DKIM if **any one** passing signature is aligned. [RFC 7489 §4.1]

## 14 · How SPF, DKIM, and DMARC Are Evaluated Together

The full mechanics promised in section 4, run in order on a received message. [RFC 7489 §4, §5]

1. **SPF evaluation** — check the RFC5321.MailFrom domain (or HELO if MailFrom is empty). Result: Pass, Fail, SoftFail, Neutral, None, TempError, or PermError. [RFC 7208 §4]
2. **DKIM evaluation** — verify each `DKIM-Signature` header; each produces an independent pass or fail. [RFC 6376 §6]
3. **DMARC record lookup** — query the `_dmarc.<domain>` TXT record for the From domain. No record → DMARC processing stops, no enforcement. [RFC 7489 §5.6]
4. **SPF alignment check** — if SPF passed, compare RFC5321.MailFrom with RFC5322.From under the configured mode (`aspf=`). [RFC 7489 §4.1]
5. **DKIM alignment check** — for each DKIM pass, compare the `d=` domain with RFC5322.From under the configured mode (`adkim=`). [RFC 7489 §4.1]
6. **DMARC disposition** — either path passes with alignment → the message passes DMARC, and policy is not applied. Neither path passes → the message fails DMARC, and the receiver applies `p=` (subject to `pct=`).
7. **Reporting** — regardless of pass/fail, authentication results are aggregated for the next aggregate report to `rua=`.

## 15 · DMARC: Aggregate Reporting

Receivers that implement DMARC reporting send aggregate reports to the address(es) in `rua=`. [RFC 7489 §7.2]

Reports summarize authentication results for a sending domain over a time interval (typically 24 hours). The format is XML, described by the DMARC XML schema. [RFC 7489 Appendix C]

**Contents**

- the policy applied at time of delivery (the receiver's view of the DMARC record);
- per-source-IP rows, each with:
  - source IP address,
  - message count,
  - disposition applied (`none`, `quarantine`, `reject`),
  - SPF result and aligned domain,
  - DKIM result and aligned domain,
  - override reasons (e.g., local policy, forwarding).

**Forensic (failure) reports** (`ruf=`) are sent per-message on individual failures; the format is similar to ARF (RFC 5965). Major receivers rarely generate them due to privacy concerns.

**Cross-domain reporting.** If the `rua=` address is on a different domain from the DMARC policy domain, the domain named in `rua=` must publish a DNS authorization record:

```
<policy-domain>._report._dmarc.<reporting-domain>  value: v=DMARC1
```

[RFC 7489 §7.1]

## 16 · Email Forwarding and Intermediary Effects

Each effect below names which step of section 14 breaks when an intermediary touches the message.

**SPF and forwarding.** An intermediary (e.g., a `.forward` alias or a mailing list server) sends from its own IP, which the original RFC5321.MailFrom domain's SPF record does not authorize. Result: SPF fails at the final destination for a legitimately forwarded message. [RFC 7208 §11.4] Some forwarders rewrite MAIL FROM to their own domain (the bounce address): that passes SPF for their domain, but loses the original domain's authentication.

**DKIM and forwarding.** Signatures survive if the signed headers and body content are unmodified; pure forwarding (relay) typically preserves DKIM. DKIM is therefore the more robust mechanism for forwarded mail. DKIM fails if: the body is re-encoded or reformatted, signed headers are modified, or new headers covered by oversigning are inserted.

**Mailing lists.** List servers commonly modify messages: `[List]` prefixes on `Subject:`, appended body footers, added `List-*` headers, or `From:` rewritten to the list address.

- Subject modification breaks DKIM if `subject` appears in `h=`.
- Body modification breaks DKIM regardless of canonicalization.
- `From:` rewriting (common for DMARC compliance of `p=reject` domains) changes the alignment domain entirely.

**ARC** (RFC 8617) lets intermediaries record the authentication state at the point they received the message, adding three headers: `ARC-Seal`, `ARC-Message-Signature`, and `ARC-Authentication-Results`. A final receiver can then know an upstream hop validated SPF/DKIM even if those results are no longer verifiable. ARC is a trust mechanism, not an authentication mechanism; receivers may choose whether to honor it.

**SRS** rewrites RFC5321.MailFrom to a domain controlled by the forwarder, preserving the original address encoded in the local part. It lets SPF pass at the next hop. It does not address DKIM or DMARC alignment.

## 17 · Common Failure Modes

Each failure mode below is a diagnosis exercise: which step of the evaluation, and which record choice, produced this outcome?

### SPF

- **Unlisted sending IP** — a new ESP, CRM, or marketing platform sends mail for the domain but its IP range is not in the SPF record. Result: SPF Fail or SoftFail.
- **DNS lookup limit exceeded** — deeply nested `include:` chains or many mechanisms consume all 10 permitted lookups. Result: PermError, which many receivers treat as Fail. [RFC 7208 §4.6.4]
- **Void lookup limit exceeded** — more than 2 DNS mechanisms returning zero records. Result: PermError. [RFC 7208 §4.6.4]
- **SoftFail instead of Fail** — `~all` means receivers accept and mark rather than reject; provides no enforcement.
- **Split-brain SPF** — different SPF records at different DNS authorities during propagation.
- **Missing MAIL FROM handling** — the domain has an SPF record but no rule covers the MAIL FROM used by automated bounce paths or subdomain senders.

### DKIM

- **Key rotation without overlap** — removing the old selector from DNS before in-flight messages are delivered makes verification fail for messages signed with the old key.
- **Body modification by intermediary** — any change to the message body after signing (line wrapping, footer addition, encoding changes) invalidates the body hash.
- **Signed headers modified** — modifications to headers listed in `h=` (e.g., `Subject` rewrite by a mailing list) break the signature.
- **Unsigned From header** — if `from` is not in `h=`, the From can be replaced without breaking the signature, defeating the signature's purpose for DMARC.
- **Weak key size** — RFC 8301 deprecates SHA-1 and sets a 1024-bit floor for RSA keys: verifiers must not treat signatures from keys below 1024 bits (such as 512- and 768-bit keys) as valid; best practice is 2048 bits.
- **Key revocation gap** — setting `p=` to empty revokes the key immediately; previously signed mail in flight will fail.
- **Missing or incorrect key TXT record** — typos in the key record, publishing at the wrong name, or TXT record truncation.

### DMARC

- **SPF alignment fails on forwarding** — the forwarded message arrives from a forwarder IP; SPF fails or aligns to the forwarder's domain, not the From domain.
- **DKIM breaks in mailing lists** — both SPF and DKIM fail for the From domain; DMARC fails even if the message originated legitimately.
- **Policy at `none` indefinitely** — no enforcement; failures generate reports but receivers take no action.
- **No `rua=` set** — no aggregate reports delivered; no visibility into which sources are failing.
- **Subdomain policy not considered** — absent `sp=`, the receiver applies `p=` to subdomains without their own record; an explicit `sp=` is required to give subdomains a different policy. [RFC 7489 §6.3]
- **Cross-domain `rua=` without authorization record** — if `rua=` points to a domain other than the policy domain, the domain named in `rua=` must publish an authorization record or reports may not be accepted. [RFC 7489 §7.1]
- **Organizational domain determination error** — different implementations of the Public Suffix List can disagree on organizational domain boundaries, causing alignment results to differ across receivers.
- **`pct=` below 100** — only a fraction of failing messages receive enforcement; attackers can retry until they land in the unenforceable percentage.
